# API トークンなどの秘匿

## 現行の方針

- 秘密は `setProxyConfig` に、秘密でない目次は `setConfig` に分けて保存する
- auto-numbering はプロキシ設定を自分で持ち、秘匿のための汎用プラグイン `api-proxy` も別に作る
- 先に auto-numbering で作り、保存の処理を共有パッケージに移してから `api-proxy` を作る
- 守れるのは秘密の値だけで、使えることは隠せない。そのため、秘密は用途（URL とメソッドの組）を絞って保存する

詳細は [proxy-config.md](../proxy-config.md)。

## 判断履歴

### 2026-11-23 auto-numbering への組み込みと汎用プラグインの両方を作る

- 背景: auto-numbering は API トークンを `setConfig` に平文で保存しており、アプリを使う全員がブラウザから読める。また、JS カスタマイズでは秘密を置く場所が無い（`kintone.proxy` にはプロキシ設定が無い）
- 検討した選択肢: (a) auto-numbering に組み込むだけ (b) 組み込みと汎用プラグインの両方 (c) 汎用プラグインだけを作り、auto-numbering もそれを使う
- 決定: (b)。外部 API を含め、JS カスタマイズからも秘密を使いたい
- 却下した理由: (a) は JS カスタマイズの用途を満たさない。(c) は auto-numbering を使うのに別のプラグインの導入と設定が要り、プラグイン ID の受け渡しも必要になる

### 2026-11-23 api-proxy は kintone REST API と外部 API をタブで分ける

- 背景: Qiita の先行例（kintone Proxy Config 設定プラグイン）は「URL＋メソッド」ごとにヘッダーと本文の JSON を書く形。kintone のトークンでは、同じ URL とメソッドで複数アプリを扱うとき、利用者が自分でトークンをカンマでつなぐ必要がある
- 決定: kintone タブはアプリごとの行で入力し、プラグインが URL ごとにトークンをつないで保存する。外部タブは先行例と同じく JSON で書く。プロキシ設定は一覧で読めないため、行の一覧は目次として `setConfig` に置く
- 却下した理由: 1つの JSON の形にまとめると、kintone のトークンのつなぎ方と9個の上限を利用者が意識する必要がある

### 2026-11-23 設定画面で秘密を伏せ字で表示し直す

- 決定: `getProxyConfig` で読み、伏せ字で表示する（切り替えで見られる）
- 却下した理由: 「設定済み」とだけ出して入力時に上書きする形は、外部タブのヘッダーの JSON を一部だけ直せない。設定画面を開けるのはアプリの管理者だけなので、表示しても漏れる範囲は変わらない

### 2026-11-23 kintone タブでは、行ごとに許可する操作を選ばせる（前の判断を覆す）

- 背景: プロキシ設定で守れるのは秘密の値だけで、アプリを開ける利用者は誰でも、保存した組（URL とメソッド）の範囲でトークンの権限を使える。トークンは利用者本人の権限とは別に働くので、範囲が広いほど、利用者が本来できない操作の範囲も広がる。`/k/v1/` 全体に4つのメソッドで保存すると、そのトークンが kintone の REST API すべてに付く
- 決定: 行ごとに「レコードの取得」「追加」などの操作を選ばせ、選んだ操作の URL とメソッドだけを保存する。auto-numbering で、採番に使う3つの API に絞ったのと同じ考え方
- 却下した理由: トークンの権限だけに任せる案は、権限の種類（閲覧・追加・編集・削除・アプリ管理）が粗く、たとえば閲覧の権限ではレコードとコメントの取得を分けられない。URL とメソッドで絞れば、二重の制限になる

旧判断（覆した）: 2026-11-23「kintone タブではメソッドを選ばせない」。GET・POST・PUT・DELETE の4つすべてに保存し、制限はトークンの権限に任せる、としていた
